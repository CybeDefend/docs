When CybeDefend scans a container image, it inventories every package the image
installs and reports the vulnerabilities affecting them. This page explains
where each finding comes from, which distributions are covered, and how to read
a result that looks unexpectedly short.

## Where a Finding Comes From

Every container vulnerability carries a `detectionSource`:

| `detectionSource` | Meaning |
|---|---|
| `scanner` | The scanner pod reported the vulnerability itself, from the vulnerability database it carries. |
| `osv` | CybeDefend matched the package inventory of the image against its own mirror of the [OSV](https://osv.dev) database. |

The field is returned by both container result endpoints:

```
GET https://api-eu.cybedefend.com/project/{projectId}/results/container
GET https://api-eu.cybedefend.com/project/{projectId}/results/container/{vulnerabilityId}
```

Both require the `read_scan_result` permission. Replace `api-eu` with `api-us`
if your organization is hosted in the US region.

In the dashboard, an **OSV match** badge marks findings with
`detectionSource: osv`. Scanner-reported findings carry no badge — they are the
historical default and need no decoration.

<Note>
  Detections recorded before this field existed read `scanner`. A scanner report
  always keeps that label, even when the OSV mirror would have found the same
  advisory.
</Note>

<Note>
  `detectionSource` is not in the generated
  [API reference](/latest/api-reference/introduction) yet — the OpenAPI spec has
  not been regenerated since the field landed. It is present in the response
  today.
</Note>

## Distributions Matched Against the OSV Mirror

A package is matched only when its distribution maps to an OSV ecosystem:

| Base OS family | OSV ecosystem | Keyed on |
|---|---|---|
| Alpine | `Alpine:v3.19` | major.minor |
| Debian | `Debian:12` | major |
| Ubuntu | `Ubuntu:22.04` | major.minor |
| Red Hat Enterprise Linux | `Red Hat` | rolling, no version |
| AlmaLinux | `AlmaLinux:9` | major |
| Rocky Linux | `Rocky Linux:9` | major |
| Wolfi | `Wolfi` | rolling, no version |
| Chainguard | `Chainguard` | rolling, no version |
| Mageia | `Mageia:9` | major |

Any other base OS — or an image whose OS the scanner could not identify — is
covered by whatever the scanner itself reports, with no OSV matching on top.

<Warning>
  OSV matching covers **operating-system packages only**. Language packages
  bundled inside an image (npm, pip, gem, Maven…) are inventoried, but they are
  not matched against the OSV mirror. Scan the repository itself with
  [code repository scanning](/latest/code-scanning/scanning-options/code-repository-scanning)
  to cover your application dependencies.
</Warning>

### Debian, Ubuntu and RPM-Based Images

OSV bounds a `deb` or `rpm` advisory with the complete distribution version —
`[epoch:]version[-release]`, for example `1:1.1.1w-0+deb11u1`. The scanner
reports those coordinates split apart (version `8.30`, release `3`, epoch), and
a truncated version cannot be compared against an advisory range without
producing false positives, so packages that did not carry the complete version
were skipped entirely. In practice, matching was limited to the apk families
(Alpine, Wolfi, Chainguard).

The scanner now sends the complete version alongside the split one, and
Debian-, Ubuntu- and RPM-based images are matched like Alpine images.

<Note>
  Images scanned **before** this change stored no complete version on their
  package rows, so they are not picked up retroactively. Re-scan an image once
  to get its Debian / Ubuntu / RPM findings.
</Note>

### Findings That Name a Package You Did Not Install

OSV keys distribution advisories on the **source** package, while the scanner
names the **binary** package that the image actually installs. An advisory for
`openssl` is therefore matched against an image that installs `libssl3`, and the
finding names `openssl`.

This is expected. The fix is the one the advisory names — upgrade the binary
package the distribution builds from that source.

### Advisory Identifiers

One advisory reaches the mirror under several identifiers. CybeDefend keys each
detection on a single canonical identifier so that the same vulnerability is not
reported twice:

- A distribution re-publication of a CVE (`ALPINE-CVE-2024-1234`,
  `DEBIAN-CVE-2024-1234`, `UBUNTU-CVE-2024-1234`) folds onto the CVE itself.
- A bulletin (`DLA-…`, `DSA-…`, `USN-…`, `GHSA-…`) folds onto its lowest CVE
  alias.
- Anything with no CVE alias keeps its own identifier.

### Fixed Version

`fixedVersion` is the smallest fix strictly above the version installed in the
image, compared with the ecosystem's own algorithm — an apk `-r9` is above
`-r7`, a dpkg `+deb10u4` above `+deb10u3`. When the advisory publishes no fix
that applies to the installed version, `fixedVersion` is empty.

## End-of-Life Base Images

Each scanned image carries `osEosl`, returned by:

```
GET https://api-eu.cybedefend.com/project/{projectId}/results/container/images
GET https://api-eu.cybedefend.com/project/{projectId}/results/container/images/grouped
```

A repository group is flagged when **any** image in it is. The flag is resolved
at every scan against [endoflife.date](https://endoflife.date), cached for 24
hours per distribution, with a 3-second timeout and a built-in table as
fallback. It never blocks or fails a scan, and a release nobody recognises
leaves the scanner's own verdict alone. The flag is refreshed on every scan, so
rebuilding onto a supported base clears it.

<Warning>
  **A short list of findings on an end-of-life base image is not good news.**
  When a distribution stops supporting a release, it stops publishing advisories
  for it. The image does not become safe; it becomes unobserved. Treat `osEosl`
  as the finding — rebuild onto a supported base rather than reading the
  vulnerability count.

  This is sharper for end-of-life Debian and Ubuntu releases: unfixed
  vulnerabilities that those distributions track in their own security trackers
  are not published to OSV for an unsupported release, so they no longer appear
  in your results.
</Warning>

## New Advisories on Images Already Scanned

The package inventory of an image is kept after the scan. When a new advisory
reaches the mirror, it is matched against the stored inventory, and findings are
created on images that were scanned before the advisory existed — no re-scan
needed.

These appear in your project's existing zero-day alerts with the type
`Container`, alongside the package name and version they were matched on.

<Note>
  This applies to OSV-matched findings. Vulnerabilities the scanner reports from
  its own database are only refreshed when the image is scanned again.
</Note>
