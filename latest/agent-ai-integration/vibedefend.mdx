<Note>
**VibeDefend is the automated path to Cybe MCP — plus everything around it.** The [Cybe MCP](/latest/agent-ai-integration/cybe-mcp) page walks you through adding the MCP URL to each client by hand. VibeDefend does that for you, and goes further: it wires a **hook layer** so the right business and security rules arrive in the agent's context *at the moment it edits code*, hard-blocks denied actions, and runs a gap analysis at the end of each substantive session. One command, every detected agent.
</Note>

## Install

```bash
npx -y @cybedefend/vibedefend@latest install
```

Works on **macOS, Linux and Windows** — PowerShell, cmd, bash, zsh, fish, Git Bash, pick any. Requires **Node 18.17 or later**, which most users already have because Claude Code / Cursor / Codex ship a bundled Node.

The installer is fully interactive: pick a region, pick which agents to wire (they're auto-detected), confirm. That's it.

Prefer a global install?

```bash
npm install -g @cybedefend/vibedefend && vibedefend install
# pnpm and yarn work the same way
```

## MCP alone vs. MCP + hooks

Connecting the MCP server by hand (the [Cybe MCP](/latest/agent-ai-integration/cybe-mcp) flow) gives your agent a **passive** security backend: it can list findings, drill into a vulnerability, drive the status lifecycle and pull business-logic context — *when you ask it to*.

VibeDefend adds the **active** layer on top. The hooks fire on the agent's own lifecycle events, so security shows up without anyone prompting for it:

| Moment | What VibeDefend does | Why it matters |
|---|---|---|
| **Before a write** (`Edit` / `Write` / `MultiEdit`, plus shell commands that write files on Claude Code and Codex⁴) | Injects the business + security rules relevant to *this* change into the agent's context. | The agent writes secure, on-policy code from the first line instead of being corrected afterwards. |
| **On any tool call** | **Action Guards** evaluate the call against your guard policy and hard-block on deny. | A `rm -rf`, a write to a protected path, or a fetch to a blocked host is stopped before it runs — not flagged after. |
| **At session start** | Loads the CybeDefend doctrine and opens the **proposals inbox** (Accept / Reject picker). | The agent starts every session knowing your rules, and you clear pending rule proposals up front. |
| **At session end** (`Stop`) | Runs a **gap analysis** once the session crosses the edit threshold. | Surfaces the business rules you relied on but never wrote down, and proposes them for review. |
| **On long sessions** (`PreCompact`) | Same gap analysis, fired before the context window is compacted. | Long sessions don't lose their rule-gap review just because the transcript got summarised. |
| **Per prompt** (Claude Code) | A lightweight doctrine backstop on every user prompt. | Keeps the CybeDefend flow intact even when another skill auto-activates and would otherwise take over the turn. |

The MCP server is what the hooks call under the hood. VibeDefend installs both, so you get the tools *and* the moments that use them.

## Supported agents

VibeDefend auto-detects and wires whichever of these you have installed. Unchecked agents stay untouched — re-run `vibedefend install` any time to toggle one on or off. A region switch is the exception: it re-points the MCP server of unchecked agents too, so none is left on the region you left.

| Capability | Claude Code | Cursor | OpenAI Codex | Windsurf | VS Code Copilot |
|---|:---:|:---:|:---:|:---:|:---:|
| **MCP server install** | ✅ | ✅ | ✅ | ✅ | ✅ |
| **Business + Security Rules** *(injected pre-write)* | ✅ edit + shell⁴ | ❌ not exposed⁵ | ✅ edit + shell⁴ | ⚠️ writes only | ✅ |
| **Action Guards** *(hard block on deny)* | ✅ all tools | ✅ all tools | ✅ all tools | ⚠️ writes + MCP fallback¹ | ❌ not yet wired |
| **Session Start** *(loads doctrine + proposals inbox)* | ✅ | ✅ | ✅ | ⚠️ proxied² | ✅ |
| **Session Review** *(end-of-session gap analysis)* | ✅ | ✅ | ✅ | ✅ | ✅ |
| **PreCompact** *(long-session gap analysis)* | ✅ | ❌ not exposed⁵ | ❌ no event | ❌ no event | ❌ not exposed⁵ |
| **Doctrine backstop** *(per-prompt reminder)* | ✅ | ❌ | ✱ via MCP³ | ❌ | ❌ |
| **Min version** | latest | ≥ 1.7 | latest | latest | ≥ 1.110 |

**Legend** — ✅ supported · ⚠️ supported with caveats · ❌ not exposed by the agent · ✱ alternate mechanism

¹ Windsurf's `pre_write_code` hook hard-blocks on file writes only. For non-write tool calls (Read / Bash / WebFetch) the installer drops a snippet into `.windsurfrules` instructing the agent to call `cybe_guards_check` via MCP before sensitive actions — soft enforcement that relies on the model following its rules file.

² Windsurf has no native SessionStart event. VibeDefend wires `pre_user_prompt`, which fires on every turn. The hook is idempotent and cheap (one GET to the proposals endpoint, returns "0 pending" once the inbox is empty), so the per-turn cost is negligible.

³ Codex follows the doctrine via the MCP server's `Server.instructions` field on each session, which removes the need for a per-prompt reminder hook.

⁴ On Claude Code and Codex the rules also load when the agent writes files through the shell — `>` / `>>` redirections, heredocs, `tee`, `sed -i`, `perl -pi`, `cp` / `mv`, `dd of=`, `bash -c '…'` — so an agent that edits from the terminal gets the same rules as one using the edit tool. Read-only commands load nothing. Inline interpreters (`python -c`, `node -e`), `git apply` / `patch`, and commands run through `xargs` or `find -exec` are not covered. On Windsurf and VS Code Copilot, rules load on the edit tools only.

⁵ On Cursor, a pre-write hook can allow or block an edit but cannot add anything to the agent’s context, so the business and security rules do not reach the agent before a write there — Action Guards still apply, since a deny is a block. Cursor and VS Code Copilot likewise expose no way for a hook to reach the agent when the context window is compacted: on those two the gap analysis runs at session end only.

## The install flow, step by step

`vibedefend install` walks you through four prompts and then signs you in.

<Steps>
  <Step title="Pick a region">
    Choose **Production — EU** or **Production — US**. VibeDefend registers an MCP server named `cybedefend` pointing at that region's endpoint and wires the hooks to call the matching Gateway — you never type a URL. The two regions are independent CybeDefend tenants; sign in to the one that hosts your account (`eu.cybedefend.com` vs `us.cybedefend.com`). Re-running `install` on the other region switches you over: you sign in again, because a stored session only counts for the region that issued it, and the MCP server of the agents you don't select this time is re-pointed as well — any VibeDefend cannot re-point is named, and `vibedefend doctor` re-points it.
  </Step>
  <Step title="Pick which agents to wire">
    VibeDefend prints a detection table (one row per agent, with a version badge) and a multi-select. Detected, supported agents are pre-checked; a version that's too old is shown disabled with an "update this client" hint; an agent you don't have yet is still selectable, so you can pre-wire hooks before you install it.
  </Step>
  <Step title="Tune the hook config">
    A handful of questions, each with a tuned default:

    - **Enable the session-end gap analysis?** — default **on**. Without it, the gap analysis never runs.
    - **Edits threshold to trigger it?** — default **1**, so the gap analysis runs after every session that touched code. An integer from 0 to 100; raise it if the nudge feels noisy.
    - **Enable automatic background updates?** — default **on**. Hooks self-refresh so you never re-run install (see [Keeping VibeDefend current](#keeping-vibedefend-current)).
    - **Enable non-blocking mode?** — default **off**. For an autonomous agent — a CI runner, an unattended agent — with nobody in the chat to answer a prompt. See [Non-blocking mode](#non-blocking-mode).
    - **Enable auto-propose mode?** — default **off** *(not recommended)*. Off means rule proposals need an explicit chat-side "yes". On means the agent drafts and pushes proposals without asking first — you still review them at the next session start. Non-blocking mode supersedes it, so the installer skips this question when you turn that on.
  </Step>
  <Step title="Sign in">
    If VibeDefend has no stored credentials, it runs the login flow automatically: OAuth 2.0 Authorization Code + PKCE opens your browser to the CybeDefend sign-in page, receives the callback locally, and stores the token bundle in your OS keychain. If your browser already has a dashboard session, this completes instantly. The refresh token persists for 14 days.
  </Step>
  <Step title="Put the proxy in front of your other MCP servers">
    Last question, yes by default: whether VibeDefend should sit in front of the MCP servers your clients already have, so each tool is checked against your organization's policy before an agent calls it. VibeDefend then takes over the sign-ins Claude Code and Codex already hold for those servers, and offers the browser for the ones left. Answer no and your client configs are left alone. See [Checking the MCP servers your agents use](/latest/agent-ai-integration/vibedefend-mcp-proxy).
  </Step>
</Steps>

## Link a project

After install, drop one tiny file at the root of each repo you want monitored — a `.cybedefend/config.json` with your project UUID:

```json
{ "projectId": "<your-cybedefend-project-uuid>" }
```

Grab the UUID from the project page on the [EU dashboard](https://eu.cybedefend.com) or the [US dashboard](https://us.cybedefend.com). You can also override it per shell or per project with the `CYBEDEFEND_PROJECT_ID` environment variable.

`vibedefend link`, run at the root of the repository, does the same for you: it
resolves the project from `--project`, from your git `origin`, or from an
interactive picker, and writes the `.cybedefend/config.json` itself. `--path`
points it at another directory, and `--region` picks a region when VibeDefend is
not installed yet.

The picker also offers **Create a new project**: pick a team, confirm the name
(the repository's, by default), and VibeDefend creates the project and links it
to its GitHub or GitLab repository through your organization's integration, which
starts the first scan. The new project comes with every AI feature on — AI merge
request, improving results, sorting vulnerabilities and Security Champion — each
one switchable in the project's settings. Creating a project takes the team
manager role, or organization creator or administrator. When your `origin` is
already linked to another project, VibeDefend creates nothing and names the
project to link instead.

<Note>
Because `.cybedefend/` is a **directory** here, the deprecated `.cybedefend` exclusion *file* cannot exist beside it — a path is either a file or a directory. Declare your SAST exclusions in [`.cybeignore`](/latest/code-scanning/scanning-options/cybedefend-ignore-file) at the repo root, or in `.cybedefend/ignore` next to `config.json`.
</Note>

### A folder with no project

The hooks are installed machine-wide, so they fire in every folder you open an
agent in — notes, a scratch directory, an unrelated repository. VibeDefend
resolves the project once, when the session starts. When the folder has no
`.cybedefend/config.json` and no CybeDefend project with VibeDefend enabled
matches its git `origin`, you get one line saying so and VibeDefend stays off
for the rest of that session: no rules before a write, no Action Guards, no
proposals inbox, no end-of-session gap analysis. Run `vibedefend link` in the
folder, and the next session starts with VibeDefend on.

A folder that does map to a project, but where you are signed out or the API
does not answer, is a different case: the line says so, nothing is switched
off, and the hooks try again on the next prompt or edit.

## In the dashboard

Once a project is linked, what your agents do on it shows up in the **VibeDefend** space of the dashboard. The sidebar carries a **VibeDefend | AppSec** switch: the VibeDefend pages live under `/vibedefend`, the application-security pages under `/appsec`, and the root `/` is no page of its own — it opens the home of the space you work in. Links CybeDefend sends you — in e-mails, Slack messages, Jira issues, pull-request comments and the CLI's output — open the right page whether or not they carry the prefix.

| Page | What you see |
|---|---|
| **Home** — `/vibedefend` | Every project you can read, searchable by name, each with the coding agent that worked on it, its rules, its guard triggers of the last 7 days and when its last diff scan ran. |
| **Overview** — `/vibedefend/organization/overview` | Key figures over the last **7, 30 or 90 days**, each against the period before: rule proposals waiting for validation, guard triggers, diff scans and the findings they caught — then, day by day, the guard outcomes, the rules served to your agents, the agents at work and the most active projects. |
| **Activity** — `/vibedefend/activity` | One timeline of the diff scans and guard triggers of every project you can read, newest first, with the agent sessions running right now and the proposals waiting for your validation. Open an event for its detail. |
| **MCP servers** — `/vibedefend/mcp` | The MCP servers your coding agents use, each with its verdict, the action the proxy applied, its flagged tools and who uses it. See [Checking the MCP servers your agents use](/latest/agent-ai-integration/vibedefend-mcp-proxy#what-your-organization-sees). |
| **A project** — `/vibedefend/project/<id>` | **Business rules**, **Security rules**, **Action Guards**, **Scan diff** and the **Code map**. |

A coding-agent session counts as running while it has called a Cybe MCP tool in the last **15 minutes**; the list holds at most 200.

### Filtering the timeline

The activity timeline, a project's guard triggers and a project's diff-scan history take the same filters:

| Filter | What you can ask for |
|---|---|
| **Period** | Events at or after a start instant, strictly before an end one. |
| **Projects** | Up to 100 at a time. A project you cannot read is left out. |
| **Who** | Up to 50 people. |
| **Agent** | Claude Code, Claude Desktop, Cursor, Codex, Windsurf, Gemini CLI, VS Code — and `unknown` for a session that declared none. |
| **Event** | A diff scan, a denied action, a warned action, and an MCP call that was refused, accepted while suspicious, passed with a warning, or whose result carried an injection. |

A diff scan carries its branch, the scanners it ran (`sast`, `iac`, `secret`), its findings by severity and who launched it. A guard trigger carries the tool the agent called, the rule that fired, and whether the call was denied or warned. An MCP call event carries the server, the tool, why it was flagged and the agent that made the call.

### The languages a security rule targets

A security rule is written for one or more of these, so the rules that reach your agent match the file it is editing — infrastructure, CI/CD and configuration files included:

`python` · `javascript` · `typescript` · `java` · `go` · `rust` · `csharp` · `cpp` · `c` · `php` · `ruby` · `kotlin` · `swift` · `scala` · `shell` · `bash` · `dockerfile` · `yaml` · `html` · `css` · `sql` · `terraform` · `kubernetes` · `github-actions` · `gitlab-ci` · `docker-compose` · `dart` · `manifest` · `firebase-rules` · `generic`

### Reviewing a project's business rules

Proposals land in the **Proposals** tab of a project's **Business rules** page two ways: the end-of-session gap analysis above, and CybeDefend's own analysis of your code after each scan. Each proposal says where it came from, and you accept it, reject it, or edit it before activating it.

Filter the list down before you work through it. Every option carries the number of proposals behind it:

| Filter | Values |
|---|---|
| **Theme** | Access control · Billing & plans · Limits & quotas · Data integrity · Privacy & secrets · Lifecycle · Integrations · Notifications · AI · Platform · Code conventions · Other · Uncategorised |
| **Kind** | Business · Security · Engineering · Operations |
| **Severity** | Info · Low · Medium · High · Critical |
| **Origin** | Code · History · Documentation |
| **Verification** | Verified · Not verified |

**Order** holds *Most reliable first*, *Most severe first* and *Newest first*. Select rows and use **Accept selected** or **Reject selected** to clear a batch in one go — at most 25 proposals per accept, 100 per reject — then read the result line for what was accepted, rejected, skipped or failed.

A proposal can carry a badge that changes what you do with it:

| Badge | What it tells you |
|---|---|
| **Corrected** | The rule was corrected against your code. The card shows the wording it replaced. |
| **Violated in N places** | The rule holds, and N places in your code break it. Open them from the card. |
| **Unverifiable** | It could not be settled from this project's code — it lives elsewhere (another service, runtime configuration) or comes from a document. Check it yourself before accepting. |
| **Obsolete** | The code the rule described is gone. Accepting it deprecates the rule. |

Proposals that contradict each other, contradict an active rule, or disagree with your documentation arrive grouped in one **Conflicting rules** card. Accept the right one and the others are rejected together.

**Re-mine rules** asks for a full pass over the project, once per project per 24 hours. While a pass is queued or running the page shows the stage it is on and how long it has been going, and new proposals appear when it finishes. A pass that could not do everything says so, and why.

### The code map

A project's **Code map** draws its code for one branch — files, classes, functions, interfaces and the HTTP endpoints that reach them. It is the same page on both sides of the **VibeDefend | AppSec** switch, so changing product keeps you on it.

| Panel | What you do with it |
|---|---|
| **Routes** | Every route of the current view, each with the authentication fact found on it — **Protection declared**, **Declared public** or **No protection found** — and the middlewares on its path. Filter by text, authentication fact, method, framework or module; sort by path, authentication fact or file. |
| **Chain** | From the selected node, the call chain **downstream** (what it calls) or **upstream** (what reaches it), from 1 to 6 hops deep, 3 by default. Each hop lists the calls, the remote services, the data read and written, and the routes leading there. The panel says when the walk stopped at its limit. |
| **Search** | Jump to a node by name, file path or route — up to 20 matches per search. |

Breadcrumbs and the URL follow your selection, so a view can be bookmarked or sent to a colleague and the browser's back button retraces your steps. A branch the map has not analysed says so; it is drawn at that branch's next scan.

#### From a finding to the map

A SAST finding with a file and a line carries a **Code map** tab: the routes that reach the vulnerable line, the call path of the route you select, the protections and middlewares found along it, and what the code touches — what it reads, what it writes, and which values arrive from the request rather than from the server. **Open in the code map** carries the whole picture to the project's map, on the branch the finding was read on.

<Note>
When no route reaches the line, the tab says so. That is what the analysis found, not a guarantee: the code can still be called another way — a job, a script, another service.
</Note>

## Commands

```text
vibedefend install            Set up MCP + hooks (interactive)
vibedefend update             Upgrade the binary if newer, then refresh hooks
vibedefend update --self      Upgrade only the CLI binary (don't touch hooks)
vibedefend status             Read-only install report (region, agents, API check)
vibedefend doctor             Diagnose the install and repair what's fixable
vibedefend link               Link the current folder to a CybeDefend project
vibedefend login              (Re-)authenticate against the CybeDefend API
vibedefend org [id]           Show or select the organization, and show its MCP policy
vibedefend uninstall          Remove the hooks, the MCP server and your credentials
vibedefend --help             Full help
```

These wrap and check the other MCP servers your agents use — see
[Checking the MCP servers your agents use](/latest/agent-ai-integration/vibedefend-mcp-proxy):

```text
vibedefend sync               Put the VibeDefend proxy in front of your MCP servers
vibedefend unwrap             Take it back out, restoring each original entry
vibedefend connect            Authorize VibeDefend against an HTTP MCP server
vibedefend scan               Reach every registered MCP server once and report
vibedefend allow <server>     Use a server even when VibeDefend flags it
vibedefend deny <server>      Refuse a server whatever the verdict
```

`vibedefend doctor` takes `--check` for a dry-run (report only, change nothing) and `--yes` to apply every fix without the confirmation prompt. `vibedefend login` takes `--force` to re-authenticate even when credentials are already stored.

`vibedefend uninstall` takes your MCP servers back out of the VibeDefend proxy, unwires the VibeDefend hooks and the CybeDefend MCP server from every agent it set up (hooks you added yourself are left alone), signs you out and deletes `~/.cybedefend/`, keeping your custom `regions.json`. It takes `--yes` to skip the confirmation prompt. The npm package itself stays installed; the command prints the line that removes it.

## Keeping VibeDefend current

At install you're asked **"Enable automatic background updates? (recommended)"**. Leave it on and you never update by hand: the SessionStart hook checks npm at most once a day and, when a newer version is published, upgrades `@cybedefend/vibedefend` in the background — the next session picks it up via the self-resolving runner shim. Opt out (or pin a version, or run in a locked-down environment) and you instead get a one-line nudge.

To update manually at any time:

```bash
vibedefend update     # upgrades the binary if newer, then refreshes hooks
```

(`vibedefend update --self` upgrades only the binary, without touching hooks.)

<Warning>
**One-time bootstrap for installs older than 1.2.0.** Those versions shipped a *frozen* copy of the hook runner with no update logic, so `vibedefend update` alone can't upgrade the binary. Do it explicitly once:

```bash
npm i -g @cybedefend/vibedefend@latest   # or: vibedefend update --self
vibedefend update                         # render the self-resolving shim
```

After that, updates are hands-off (or one `vibedefend update`) as above.
</Warning>

## Usage and monthly limits

VibeDefend is billed by usage, in three units. Each one has its own free allowance
every calendar month, for the whole organization, and the allowances reset on the
1st:

| Unit | What counts as one | Free each month |
|---|---|---|
| Rule injections | A hook fetching the security rules for your agent | 1,000 |
| Guard judgments | An Action Guard deciding on one tool call | 500 |
| Diff scans | A scan of what a session changed | 100 |

Without a card on file, usage stops at the free allowance and starts again next
month. To go further, an organization administrator or a billing manager adds a
card on VibeDefend's **Usage & billing** page. Each unit is then billed past its
free allowance, up to a **monthly cap** per unit.

Caps are proposed when the card is added and scale with the number of members in
the organization. You can raise, lower or remove each one; a cap you set by hand
stays yours and is never adjusted for you again, and resetting a unit puts it back
on the recommended cap. A unit that reaches its cap stops until the cap is raised
or the month ends.

The same page shows the month's usage per unit — current, projected to month end,
free allowance and cap — broken down by project and by member. Stopping usage
billing invoices the month's usage and puts the organization back on the free
allowance.

### Under a VibeDefend contract

If your organization holds a VibeDefend contract, usage counts against the volume
of that contract and is never billed by usage. VibeDefend's **Usage & billing**
page shows the contract, the date it ends and your CybeDefend contact, and each
unit is measured against its **contract volume** rather than a free allowance and
a cap.

A card and spending caps are not used under a contract: those controls are hidden,
and the API answers `409 CONTRACT_ACTIVE` on the checkout and the cap routes.
Going past the volume planned in the contract does not stop your agents — the page
says so, and your CybeDefend contact gets in touch. A unit stops when it reaches
the usage limit of the contract.

### When VibeDefend stops

Your agent is told which unit stopped and why, and not to retry. Each of these
needs an organization administrator or a billing manager:

| Reason | What to do |
|---|---|
| The month's free allowance for that unit is used up | Add a card, or wait for the 1st of next month |
| The unit's monthly cap is reached | Raise or remove the cap |
| A VibeDefend usage invoice is unpaid | Pay it — every VibeDefend feature is paused until it is |
| VibeDefend is not activated for the organization | Activate it in organization settings |
| The organization's VibeDefend contract reached its usage limit | Contact CybeDefend — a card or a cap cannot lift it |

## Tunables

The hook settings are chosen at install and stored in your VibeDefend config. To change them, re-run `vibedefend install` and answer the hook-config prompts again:

| Setting | What it controls |
|---|---|
| Review threshold | Edits before the session-end gap analysis fires (default `1`, so it fires after every session that touched code; 0 to 100). |
| Auto-propose | Whether the agent proposes rules without asking you first (default off). |
| Non-blocking | Whether any hook pauses for a chat-side Accept / Reject (default off). |

### Non-blocking mode

By default the agent pauses for you on business-rule proposals: an Accept / Reject picker for the pending ones at session start, and a "Propose this rule? Yes / No" at the end of a session. An autonomous agent — a CI runner, an unattended agent — has nobody in the chat to answer, and the session stalls on the question.

Turn non-blocking mode on and no hook asks anything. Pending proposals are left for a human to accept or reject in the dashboard, the agent never triages them itself, and the end-of-session gap analysis pushes its single proposal straight to the inbox. Non-blocking mode supersedes auto-propose.

### Environment overrides

These are read live from the environment, so you can set them per shell, per project, or on one agent's process only — the same machine can serve a human interactively and an autonomous agent in non-blocking mode:

| Variable | Effect |
|---|---|
| `CYBEDEFEND_REVIEW_THRESHOLD` | Edits before the session-end gap analysis fires. An integer from 0 to 100; anything else leaves the installed value in place. |
| `CYBEDEFEND_AUTO_PROPOSE` | `1` proposes without asking, `0` asks first. |
| `CYBEDEFEND_NON_BLOCKING` | `1` stops every hook from asking, `0` brings the prompts back. |
| `CYBEDEFEND_PROJECT_ID` | Override the project UUID from `.cybedefend/config.json`. |

For the three flags, `1`, `true`, `yes` and `on` read as on, `0`, `false`, `no` and `off` as off, and each wins over the installed setting in both directions. An unset or unrecognised value leaves the installed setting in place.

## Codex setup gotcha

Codex 0.131+ requires you to approve each hook from the `/hooks` panel **inside Codex** *before* it fires. After running `vibedefend install`, open Codex, run `/hooks`, and trust the `cybedefend` entries — until you do, the panel shows `Installed N / Active 0` and the hooks stay dormant.

## VibeDefend or the manual MCP setup?

Both connect your agent to the same CybeDefend tenant. The difference is how much of the platform comes along.

| | VibeDefend | [Manual MCP setup](/latest/agent-ai-integration/cybe-mcp) |
|---|---|---|
| **Setup** | One command, all detected agents at once | Edit each client's config file by hand |
| **MCP tools** (read findings, triage, context) | ✅ | ✅ |
| **Rules injected before each edit** | ✅ | — |
| **Action Guards (hard block)** | ✅ | — |
| **Session-end gap analysis** | ✅ | — |
| **Best for** | Day-to-day coding where you want security in the loop automatically | Any MCP client VibeDefend doesn't auto-wire (Continue, Cline, Zed, Claude Desktop…), or when you only want the read/triage tools |

You can also do both: run VibeDefend for the agents it supports and add the raw MCP URL by hand to any other client.

## Troubleshooting

<Accordion title="Codex shows `Installed N / Active 0`">

Codex gates hooks behind manual approval — see [Codex setup gotcha](#codex-setup-gotcha) above. Open Codex, run `/hooks`, and trust the `cybedefend` entries.

</Accordion>

<Accordion title="Hooks don't seem to run after install">

Run `vibedefend status` for a read-only report of region, wired agents and a live API check, then `vibedefend doctor` to diagnose and repair what's fixable (`vibedefend doctor --check` reports without changing anything). If the session opened with a line saying CybeDefend is off for this session, the folder maps to no project and every hook is skipped — run `vibedefend link` there, and see [A folder with no project](#a-folder-with-no-project).

</Accordion>

<Accordion title="It asked me to sign in even though Codex was already connected">

Expected, once. Codex's MCP-scoped token (`aud: cybedefend-mcp`) has limited Permify rights and can't call the Gateway endpoints the runtime hooks use, which need a user token (`aud: cybedefend-api`). They aren't interchangeable. One Logto sign-in (instant if your browser already has a dashboard session) issues the right token; the refresh token then persists for 14 days.

</Accordion>

<Accordion title="I pin versions / run in a locked-down environment">

Decline the "automatic background updates" prompt at install (or it's disabled automatically when VibeDefend can't self-resolve a global install). You then get a one-line nudge when a new version ships and update on your own schedule with `vibedefend update`.

</Accordion>

<Accordion title="My agent says VibeDefend stopped and told it not to retry">

A usage limit was hit, or VibeDefend is paused for the organization. The message
names the unit and the reason — see [When VibeDefend stops](#when-vibedefend-stops).

</Accordion>

<Accordion title="I'm on Windows">

Fully supported — no Git Bash or WSL required. The hook runner is a single bundled Node script that runs the same way on Linux, macOS and Windows.

</Accordion>
